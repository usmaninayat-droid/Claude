Sections 2–4

Why the module exists

IWMP today runs without a standardised project hierarchy. Municipal and commercial operations — two fundamentally different business models — are not cleanly separated, and every project is structured differently. The document states the consequence plainly: resources and routes are mapped differently from one project to the next, reporting and billing rely on manual workarounds, KPIs cannot roll up reliably, and every new contract is onboarded as a one-off exercise.

There is no governed structure to which routes, assets, workforce, bins, tickets, and billing transactions attach. Without it the platform cannot give management a reliable project-level view of cost, performance, or compliance, and it cannot absorb new contracts repeatably.

The future state, in one sentence

One governed module with two project categories — Municipal and Commercial — each with a defined hierarchy down to assets and workforce, where every record in IWMP attaches to exactly one node. The module becomes the operational project master inside IWMP, while Oracle ERP remains the commercial system of record.

Section 5

Scope, and what this module is explicitly not

Scope clarification, verbatim in intent

This is a core business module governing the project organisational structure and operating model for waste operations. It is explicitly not a generic task tracker — not MS Project, not Jira. Its purpose is classification, hierarchy, master creation, activation, contract-to-operations mapping, lifecycle, and governance.

In scope

  • Project structure — municipal and commercial creation, hierarchy, classification.
  • Project lifecycle — activation, hold, closure, renewal, extension, amendment.
  • Operational mapping — route, asset, workforce, bin, site, and service mapping to nodes.
  • Oracle reference linkage — consuming customer, contract, and pricing-basis reference (read only).
  • Governance — approval workflow, validation rules, audit trail, role-based access.
  • One-off jobs — short-cycle commercial workflow with an advance-payment gate.
  • Operational reporting — portfolio, KPI roll-up, exception and integration reports.

Out of scope

  • Customer and contract commercial mastery, pricing, invoicing, payment — Oracle ERP.
  • Financial accounting, general ledger, revenue recognition — Oracle ERP.
  • CRM, lead, opportunity, quotation lifecycle — Oracle ERP.
  • Route planning, tour generation, dispatch execution — IWMP Route Management, separate BRD.
  • Asset maintenance and workforce HR mastery — Asset / Workforce modules; PMM consumes mapping only.

Section 11

The two hierarchies

The hierarchy is described as the structural heart of the module. Each node has a defined parent, defined children, and defined business rules. The level count is itself the specification — municipal runs eight levels, commercial six.

Municipal hierarchy

The LOT is the contractual and allocation boundary. Districts break LOTs into service areas; routes are planned per district and locked to their LOT.

1Municipal ProjectProject type = Municipal
2Client (Tadweer Group)One client node per contract owner
3ZoneGeographic grouping of LOTs
4LOTContractual & allocation boundary; master-data domain
5DistrictService area within a LOT
6RoutePlanned per district, locked to LOT
7AssetsInherit the LOT of their assignment
8WorkforceInherit the LOT of their assignment

Commercial hierarchy

Client and contract are Oracle-owned and read-only; IWMP owns everything beneath. Assets and workforce are assigned at service-line level.

1Commercial ProjectProject type = Commercial
2Client ClassificationCategory 1–6 by contract value
3ClientCustomer account — Oracle system of record
4ContractCommercial agreement — carries IWMP codes
5Service LocationPhysical service point / site
6Service & Waste TypePaired from the IWMP catalogues
LOT master-data domain rule

Each LOT carries a domain flag the module must hold as an attribute: LOT 3 is full-overwrite, while LOT 4 and LOT 5 are append-only. This governs how master-data synchronisation behaves for records in that LOT. The document flags an assumption that this is a data-load governance rule applied during master-data refresh, not a per-transaction operational lock.

Why the contract references codes, not names

Because contracts reference IWMP classification codes rather than names, the service and waste taxonomy can be refined, re-described, or extended in IWMP without changing the contract or triggering commercial re-paper. The code is the stable contract anchor.

Section 11A

Waste & service classification — where the boundary inverts

A new capability folded into this module, and the one place where the Oracle relationship runs the other way. IWMP authors and versions the classification lists; Oracle consumes them as read-only reference. This is deliberate — it is what makes taxonomy edits commercially non-impacting.

Two parallel two-level hierarchies

HierarchyLevel 1Level 2Attributes carried on the type
Waste13 categories WC-##64 typesRecyclable flag, hazardous flag, hazard class, Bolisaty class
Service9 categories SC-##46 typesBillable flag, default SLA, default container type

The sub-type level is retired — former granular variants are absorbed into the Type description. Hazard, recyclability, billable status, SLA, and container defaults are attributes, never separate branches.

Bolisaty regulatory alignment

Each waste type maps to the Abu Dhabi Government BOLISATY four-class model, carried as a reference attribute so regulatory traceability survives while the operational hierarchy stays optimised for collection, treatment routing, and billing.

Bolisaty classMeaningExample types
PutrescibleBiodegradable / decomposingHousehold waste, food waste, green & garden waste
Non-Putrescible Non-RecyclableInert residual, not recoverableGeneral mixed waste, public area waste, mixed bulky
RecyclablesSource-segregated recoverablePaper & cardboard, plastics, metals, glass, tyres
HazardousControlled handlingChemical waste, batteries, healthcare, WEEE

Where a standard and operational logic conflict, the operational structure wins and the regulatory code is retained as a reference field.

Code-stable, name-flexible

Codes are immutable and never recycled, with reserved expansion ranges (WC-14–WC-20, SC-10–SC-15). Names and descriptions are editable under MDM dual-approval. Nodes are deactivated, never deleted. Four requirements cover this: FR-PMM-24 FR-PMM-25 FR-PMM-26 FR-PMM-27

Section 12

Lifecycle and the two-gate model

Every project moves through a defined lifecycle, and operational activation in IWMP is deliberately distinct from commercial approval in Oracle.

Status definitions

DraftStructure being built — entered on project initiation→ Pending Approval, Cancelled
Pending ApprovalAwaiting operational sign-off — hierarchy complete and valid→ Active, Draft (rework)
ActiveLive and operational — approved, plus contract approved or municipal structure confirmed→ On Hold, Closed, Amended
On HoldTemporarily paused by suspension event or decision→ Active (resume), Closed
AmendedUnder an approved change→ Active
ClosedOperationally ended — no active routes or resources remain→ Renewed (new term)
RenewedNew or extended term active, synced from Oracle→ Active
Two separate status attributes — a common modelling mistake

Commercial approval status is owned by Oracle and consumed as read-only reference. Operational activation status is owned by IWMP. These must be modelled as two separate attributes, not collapsed into one field. A commercial project cannot activate operationally if the Oracle contract is not in an approved commercial status, unless an explicit, audited exception is granted.

Lifecycle variants

Municipal· Structure confirmed→ Hierarchy built→ Approved→ Active→ Closed→ Renewed
Commercial· Oracle contract approved→ Staged in IWMP→ Hierarchy built→ Approved→ Active→ Closed
One-off job· RFQ→ Quotation→ Advance payment→ Temp allocation→ Execution→ Auto-close

Described as the most important integration in the module, and the mechanism by which the commercial/operational boundary is held. Three creation models were evaluated.

Integration mechanics

  • Trigger events — contract approved, amended, site added, service added, suspension, termination, renewal.
  • Direction — primarily Oracle → IWMP. IWMP → Oracle only for billable-transaction references, handled by Billing rather than PMM.
  • Frequency — event-driven near-real-time preferred, with scheduled batch as fallback.
  • Validation — referential integrity, mandatory fields, and hierarchy rules checked at staging, before activation.
  • Error handling — failed records quarantined with a reason and surfaced on an exception report. No silent loss.
  • Reprocessing — quarantined records can be corrected and resubmitted; idempotent by Oracle reference key.

The one-off job gate

FR-PMM-14 is the sharpest rule in the set: advance payment is a hard gate — no scheduling without it. Resources are allocated for the job window only, the job auto-closes on completion, and HV-05 prevents silent conversion into a recurring project.

Data model rules

  • Numbering — type-prefixed configurable sequences: MUN-yyyy-nnnn, COM-yyyy-nnnn, OOJ-yyyy-nnnn.
  • Soft delete — entities use an active flag and archive state rather than hard delete, preserving audit and reporting lineage.
  • Uniqueness — a route_link enforces one active project node per route.
  • Versioning — amendments and approvals preserve full before/after history for structural changes.

Segregation of duties

The role that builds a project structure cannot be the role that approves its activation. Read access to Oracle reference fields is broad; write access to those fields does not exist in IWMP at all.

Audit and traceability

  • Every create, edit, status change, approval, and mapping action logged with user, timestamp, and before/after values.
  • Approver identity, decision, comments, and attached evidence retained for each approval.
  • Each Oracle→IWMP transaction traceable by reference key, with sync status and error detail.
  • Activation records the gates passed — commercial approval and hierarchy approval — plus the approver.

Assessment

How the prototype measures against this

Reading the standalone Project Management page against the BRD, the covered ground and the gaps fall out cleanly.

Covered

Project master list — UI-01

Search, type filter, status chips, sortable table, and summary counts are all present and match the specified layout and key fields closely.

Covered

Contract-linked view — UI-06

The project detail popup's Contracts tab shows the parent contract with read-only Oracle reference fields, which is the shape UI-06 asks for.

Covered

Site & service data — FR-07

Locations and Service Lines tabs carry frequency, SLA, and status, with data ownership sitting on the project as the BRD requires.

Missing

Hierarchy builder — UI-03, 04, 05

Three of the nine specified screens are tree-based structure builders, and FR-PMM-04 is named as sprint-one foundation work. The prototype has no tree view — locations and service lines are flat tables.

Missing

Municipal projects entirely

The prototype models only commercial projects. The eight-level Zone→LOT→District structure, the LOT domain flags, and the municipal dashboard have no representation.

Partial

The two-gate status model

Section 12.2 requires commercial approval and operational activation as two separate attributes. The prototype carries a single project status field, so the gate that BR-15 describes cannot be expressed.

Missing

One-off jobs — Category 6

The seven-step short cycle with the advance-payment hard gate is a distinct workflow with its own screen. Nothing in the prototype covers it.

Missing

Client categorisation 1–6

Categories drive account ownership, SLA depth, and executive reporting, and appear as a filter dimension on UI-01. The prototype filters by waste type instead.

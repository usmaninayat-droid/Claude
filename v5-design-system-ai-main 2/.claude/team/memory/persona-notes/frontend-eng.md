## Token substitution (hex → token)
- White chrome text/icon on brand surfaces → `var(--primary-foreground)`. Sidebar active-pill/icon → `var(--sidebar-primary)` (bg) + `var(--sidebar-primary-foreground)` (icon) — NOT `var(--primary)` (sidebar has its own on-brand-vs-on-white semantic pair per theme). `text-white` on a checked glyph over `bg-primary` (selectable-card/role/app/category) is the same anti-pattern → `text-primary-foreground`. Exception: `color-picker.tsx`'s swatch check (contrast vs an arbitrary user hex) — leave it.
- Translucent overlay (`rgba(255,255,255,.2)`) on a brand bg → `color-mix(in srgb, var(--primary-foreground) 20%, transparent)` — the established "token at N% opacity" idiom (25+ files). Status dots/pills → `var(--status-{error,warning,success})`, never raw hex even when it "matches".
- `var(--success-500, #12B76A)`-style fallbacks are a smell (the fallback dupes an existing token → simplify). Figma-family components use `--fig-*` tokens, not the generic semantic ones. Tailwind v4 `@theme inline` makes `text-success`/`bg-destructive` first-class utilities — prefer them over `text-[var(--status-success)]`.

## Gate mechanics (fast, run after each batch from DS root with a trailing `.`)
- coherence.mjs: flags `#hex` on non-comment/non-SVG lines in `src/components/**`. Block-comment continuation lines must each start with `* ` or they trip the scan. `COLOR_SOURCE` (leaflet-map/map-*/config-bridge/pipeline-right-panel) is fully exempt; elsewhere use a trailing `// coherence-allow — <reason>` on the exact hex line. `color-mix(..., var(...))` never trips it (no literal hex).
- a11y-static.mjs (run alongside coherence — sub-second): icon-only button/link w/o accessible name · img w/o alt · positive tabIndex. build.sh = pure `tsc --noEmit` typecheck. Also run roundtrip.mjs + hydration.mjs + vocab.mjs (all per-edit via PostToolUse). roundtrip.mjs = G-ROUNDTRIP (save handler persists every Draft field — drop-on-SAVE). hydration.mjs = G-HYDRATION (its MIRROR, drop-on-LOAD): an edit-path `initial` reading `drafts[…]` must carry a `*ToDraftSeed(` fallback + every `onSaveDraft` must thread a `closeOnDone` discriminator; opt out via `// hydration-allow <reason>`. The seed-omits-a-row-field / composite-corruption remainder is a review-fix QA checklist item. vocab.mjs = G-VOCAB (app-shell + navigation chrome bakes no un-overridable fleet words; exempts `?? '<word>'`; opt out via `// vocab-allow <word> — <reason>`).

## Draft persistence — the recurring data-loss family (audit EVERY time a block persists a sheet's Draft)
- **Round-trip audit:** when a block persists a config-driven component's Draft into a display row, check EVERY draft field is kept — TS won't flag a silent drop (the row's local type just omits it). Fix by EXTENDING the row type with the missing fields as OPTIONAL round-trip slots (`description?`/`appIds?`/`privileges?`/`modules?`/`roleIds?`), importing the sheet's own types (don't redeclare). `initial` for an edit sheet must carry the FULL draft, not `{id,name}`, or later steps reset to empty.
- **Empty ≠ no-change:** `list.length ? d.list : prev.list` (fallback-to-previous-on-empty) silently reverts a deliberate clear-all edit. An empty array from a controlled form is intent — never special-case empty as "ignore".
- **Save-as-draft is a distinct write-path:** wiring `onSaveDraft={submit}` where `submit` resets `editingId=null` mints a duplicate per click. Fix: `upsert(d, closeOnDone)` — draft (false) captures the minted id into `editingId` + keeps context + leaves the sheet open; final (true) resets after writing.
- **Combine/split asymmetry (drop-on-load subtype):** a display string built at submit (`` `${code} ${phone}` ``) needs the REVERSE split at seed-time (`CODES.find(c => stored.startsWith(c.code))` → matched split, else `{code:'', phone:stored}`), or editing an untouched seed double-prefixes it. Grep for any `` `${a} ${b}` `` built from two draft fields and verify the inverse split exists in `*ToDraftSeed`.
- **`canProceed` can BE the drop-on-load blocker:** a step gated on "≥1 named X" + a `*ToDraftSeed` that never seeds X = editing a seeded row is permanently save-blocked (a dead-end worse than silent loss). Fix BOTH: seed the field (a `SEED_X` map keyed by id) AND relax the gate for edit (`isEdit || d.x.some(...)`) — require-on-create only.
- **Carry the id, derive the label:** prefer a row's optional raw round-trip field (`roleIds?`/`appIds?`/`modules?`) over reverse-mapping a display projection back to ids by name (breaks on rename). Populate it in seed data, with the name-reverse-map only as a fallback. Never hash a raw id (`id.toUpperCase()`) for a label — export the option catalogue (`DEFAULT_APPS`) and `.find()` into it (Law-4 single source).

## Shared shells & Law-4 config
- **Extract on the 2nd occurrence, not copy:** `StepWizardSheet` (add optional props like `secondaryAction.disabled` back-compat, don't fork the footer), `SelectableCard` (a `trailing?: ReactNode` slot absorbs hand-rolled duplicate rows), `LabeledSelect`, and a `FilterPill` (single/multi — extract at its 3rd occurrence). Check whether a "fix N places" item is really "extract, then fix once".
- **Lift domain vocab to a `DEFAULT_*` prop** (mirroring `DEFAULT_APPS`/`DEFAULT_COLOR`) — but it's only half-done until you thread it through every reference: a **recursive child** (`RuleGroupEditor` used `TRACKERS` 2 levels deep) and a **seed factory called before props exist** (`blank()`/`emptyRule()` hardcoding `'Speed'`). Hoisting an inline `as const` options array to `export const DEFAULT_X_OPTIONS` + optional prop is a ~5-line zero-risk Law-4 win — do it opportunistically when already in the file.
- **Single-item vs bulk needn't be two components:** one sheet keyed off `selected.length > 1` for the title + an extra "Selected" list section. `DEFAULT_CATALOGUE`-as-a-prop is the default for any "assign to X" picker.
- **No cross-module-folder imports outside primitives/shared:** a `events/` component must NOT import Settings' `field-select.tsx` even if identical — re-implement the ~15-line local version (layering).

## a11y idioms
- A linear wizard's step indicator is `<nav aria-label>` of buttons with `aria-current="step"` — NOT `role=tablist/tab/aria-selected` (steps aren't independent panes; later ones are `canProceed`-gated).
- A custom `role="radiogroup"`/listbox needs real arrow-key roving to be more than decorative — no deps: `onKeyDown` on the container computing `(i + dir + n) % n`, off the SAME options array the buttons map (radiogroup) or via `querySelectorAll('[role="option"]')` + `document.activeElement` index (popover list). Radix Popover already owns Escape + focus-return, so only wire Arrow/Home/End/Enter/Space.
- Radix `Checkbox` `checked` takes `boolean | 'indeterminate'` — a header select-all is `allChecked ? true : someButNotAll ? 'indeterminate' : false`.
- A checkbox INSIDE a card whose body is one big `<button>` is interactive-nesting (Radix Checkbox is itself a button) — split into an outer `<div>` with the checkbox as a SIBLING of the inner content `<button>`.
- Adding `aria-label={label}` to a "caption-above-value" trigger REPLACES the accessible name (the current value stops being announced) — a real tradeoff, not a free win; flag it, don't assume it's strictly better.

## Layout / interaction gotchas
- A custom `Select`/combobox trigger that must match a sibling `FloatingLabelInput` is a GEOMETRY match — copy its container classes verbatim (`h-14 rounded-md border bg-input-background`), don't guess `rounded-lg`/`bg-card`.
- `draggable` on a whole reorderable row breaks native input caret/selection (FF/Safari) — put `draggable`+handlers on the grip HANDLE only, `draggable={false}` on the row. Guard the DnD payload: `Number('')` is `0` not `NaN` — check the raw string is non-empty before parsing (a stray external drop reorders to index 0).
- **Selection-vs-filter drift** (distinct from drop-on-save/load): memoize the filtered/visible list (`useMemo(..., [rows, ...filterInputs])`) and make BOTH the reconciling `useEffect([visible])` AND the header indeterminate calc read that ONE memo, never raw `rows` — else the bulk-bar count lies. Portable to any list gaining multi-select. Relatedly, per-tab COUNTS for a new filter dimension compute off the base filtered by everything EXCEPT that dimension (`baseForCounts`), so switching tabs doesn't make sibling counts jump.
- A status/role pill is TINT / SOLID / OUTLINE **per column**, not a free choice: Status column = SOLID (`bg: tone, text: primary-foreground`); Roles/tag column = OUTLINE (`border: tone`, transparent bg, `text: tone`) — same `tone`, three treatments. Don't reuse the first pattern verbatim for a similar-looking pill elsewhere.
- An unselected/addable chip should be a separate NEUTRAL `border-border` button, not `TagChip` with `onRemove` doubling as add — the per-tag DATA colour is only meaningful once selected. A "grows-with-content" input = HTML `size={Math.max(min, value.length+pad)}` + `max-w-[…]` (cheaper than hidden-span measuring). An in-sheet destructive action (reversible by cancel) = a local two-stage `click → "Confirm" → click` reset on blur/close, no new dialog primitive. WCAG-clamp a per-record DATA colour by clamping only the TEXT via `color-mix(color, --foreground)` at high luminance — leave the tint/dot on the raw colour; don't add a new visual element to fix contrast.

## Consuming the DS from a product (ifm-workforce)
- **Barrel gaps:** `app-shell/index.ts` omits `MonitoringZone`/`MonitoringPoi` (and `map`/`charts`/`widgets-v2`). A product can't edit the DS — deep-import the type (`@ds/components/app-shell/types`) / module (`@ds/components/map`). Grep the barrel's export list before assuming a `types.ts` export is reachable.
- **Cross-check the real registry/union, not the ticket or comment language.** A fixed facility uses `kind: 'site'` (a real MarkerKind with a teardrop glyph), NOT `assetType: 'workforce'` — the asset-glyph registry has only `default-workforce` on disk, so a wrong slug renders a pin with no inner icon; validate assetType strings against `ASSET_VECTOR_KEYS`/actual `assets/vectors/**` filenames. Unions are narrower than they read: `CompareBars` tone is `success|warning|error|info` (no `critical` — map to `error`). A `MonitoringModuleData` gets `hybrid`/`map` views ONLY if `ModuleConfig.tabs` lists them (`{id:'map',kind:'map'}`) — providing `data.map` alone does nothing; copy `workshop.config.tsx`'s assets 4-tab shape.
- In a multi-agent build where sibling config files aren't written yet, whole-product `tsc` legitimately fails on their TS2307 lines — verify your own scope with `tsc --noEmit 2>&1 | grep your/files`, don't read "BUILD: FAIL" at face value.

## MapView camera race (T-033, zones/POIs kit-lift) — the load-transition clobber
- **A `MapViewHandle.flyTo/fitTo` call made during the map's async style-load window gets silently overwritten.** `MapView` has TWO effects keyed on its `loaded` boolean (`[center,zoom,loaded]` "keep camera in sync" + `[loaded, fitToContent]` "fit on load") — both correctly no-op before load, but BOTH also re-fire the instant `loaded` flips true, unconditionally re-applying the ORIGINAL `center`/`zoom` props / full-content bounds. If a consumer's row-click (`selectZone`/`selectRow`) calls the imperative `fitTo`/`flyTo` while tiles are still loading, the delayed `load` event fires moments later and stomps the user's camera move back to the stale state — reproduces as "the row highlights + a toast fires but the map visibly does nothing," a symptom that looks like a dead click, not a race. Fix (now in `map-view.tsx`): (1) the sync-effect skips its FIRST run via a `skippedInitialSync` ref (init camera is already set at `new maplibregl.Map({center,zoom})` construction — the effect only needs to react to genuine LATER prop changes, so drop `loaded` from its deps entirely); (2) a `userMoved` ref flips true inside every imperative handle method (`flyTo`/`fitAll`/`fitTo`), and the one-time `fitToContent` effect checks `!userMoved.current` before firing. Diagnose this class of bug by logging camera zoom/center immediately after your imperative call AND ~800ms later — a value that reverts (not just "doesn't change") means a later effect is winning, not that your call failed.
- **Debugging a "click does nothing" map interaction:** don't assume the click handler didn't fire — verify with a temporary `console.log` at each hop (row handler → `mapRef.current` truthy → the MapView method body → before/after `map.current.getCenter()/getZoom()`) via a disposable puppeteer script that pipes `page.on('console', …)` (shoot.mjs doesn't surface console output). A silently-overridden animation looks identical to a no-op from a screenshot alone.
- **`shoot.mjs`'s `--click text:/aria:` only matches `button, a, [role=button], [role=tab]`** — a table `<tr onClick>` row is invisible to it (search a filtered-to-one-row list + `css:table tbody tr` instead). When TWO elements share the same `aria-label` (e.g. a rail nav item AND an in-map toolbar button both labelled "Zones"), the regex-anchored `aria:^Zones$` matches whichever comes FIRST in DOM order (usually the rail, not the one you want) — write a one-off puppeteer script with `querySelectorAll(...)[n]` to disambiguate rather than fighting the harness.

## Consolidating overlapping modules into one (T-053) — dashboard-type composition gotchas
- **`TOOLBAR_TYPES` (AppShell.tsx) is `{'entity','pipeline'}` only** — an `entity` module gets the shell's search+facet toolbar for FREE (rendered above `render(ctx)`, feeding `ctx.query`/`ctx.facetFilters`/`ctx.sort`). Re-homing that module as a TAB inside a `dashboard`-type composite module loses that toolbar entirely (dashboard isn't in the set) — the view must grow its own self-built search+filter row (`SearchMd`+`pl-8`+"Search anything here" + single-select `Select`s for what were multi-select facets) or search/filter silently stops working with no type error. `ctx.openDetail` still works fine regardless of type (unrelated to `TOOLBAR_TYPES`).
- **Composing a former standalone module as a plain-component tab**: a `type: 'dashboard'` + `tabKind: 'instance'` + module-level `render: (ctx) => { switch(ctx.activeTab.id) {...} }` — this OVERRIDES the module type's built-in renderer entirely (bypasses `ctx.activeTab.render()`), so any owned surface (a registered custom `ModuleType` like `scheduler`, or an `entity` module with a `render` override) can be composed as a plain function component with no shell machinery at all. If a source module was behind `registerModuleType`, drop the registration — the plain component slots in directly once nothing routes through the rail by that type anymore.
- **Module-restructure-overreach** (client escalation class): feedback about a REPORT/CONTENT inside a module is never a mandate to rename/restructure the module itself (T-046 folded 'Reports' into 'Timesheet & Reports' when asked to fix one report inside Reports). When a later ticket corrects this, extract each surface back into its own file/module as a THIN composition (re-homing, not a rebuild) — keep the owning file's logic/store-wiring untouched, only change what renders it and where.
- Cross-reference sweep after an id/module rename: grep `moduleId:`, `openModule(`, permission-area/RBAC catalogs (roles' `areaIds`), and `target:` notification descriptors — a consolidated module needs exactly one new id everywhere the old ids appeared as NAV targets (a generic feature catalog like "Application Management modules" describing a physical device/app's touch-points is a DIFFERENT, narrower concept — don't rename entries there just because the words match).

## Local dev/QA harness gotchas
- **A stale `vite` dev-server process silently serves OLD rail/module labels** even after source edits — HMR can wedge (e.g. after a big module-array/import restructure) without visibly erroring. If a `shoot.mjs` screenshot shows content that doesn't match the code you just wrote, don't assume the code is wrong — `netstat`/kill the process on that port and start a fresh `vite` before re-shooting.
- **`shoot.mjs`'s `--delay N` flag is NOT per-action** — every occurrence overwrites the same `o.delay`, so only the LAST one applies, and only ONCE at the very end (before the final screenshot). Between `--click`/`--type` actions the gap is a fixed hard-coded 500ms, win or lose. A heavy transition-based mount (`React.startTransition` login→AppShell swap) can exceed 500ms, so the very next `--click` in the same invocation can race and fail with "click target not found" even though the element exists moments later. Fix: pad extra time with harmless `--click "css:body"` steps between the real actions (each adds another 500ms gap; `css:` kind clicks ANY selector via `querySelector`, not just button/a/role, so `body` never fails).
- One-off diagnostic puppeteer scripts (dumping aria-labels etc.) need `puppeteer-core`, which only lives in the DS root's `node_modules` — plain `node script.mjs` from elsewhere 404s on the import (`NODE_PATH` doesn't help ESM resolution). Write the script as `.cjs` (wrap top-level `await` in an `(async () => {...})()` IIFE) and run with `NODE_PATH=".../V5 Design System - Ai/node_modules" node script.cjs` — CommonJS `require()` DOES honor `NODE_PATH`.

## Status/category colour sets — literal-hex duplicates hide inside the token names (T-035)
- **Token NAMES don't guarantee distinct colours.** `--chart-4` and `--chart-accent-green` are both literally `--status-success`'s hex (`#12B76A`); `--chart-accent-purple` duplicates `--chart-3` (`#9E77ED`); `--chart-accent-cyan` duplicates `--chart-2`. A hash-based "pick a token per category" palette (industry colour, tag colour) can silently assign the SAME rendered colour to two conceptually different members just by including both aliases in its candidate list — grep the actual hex in `tokens/theme.css` before building any `Record<Category, token>` or hash-to-token array, and hand-pick one alias per distinct hex. A cycling `TOKENS[i % TOKENS.length]` map is *guaranteed* to repeat once the category count exceeds the token pool — prefer an explicit `Record<Union, token>` (TS enforces exhaustiveness + catches a missed case) over modulo cycling whenever the union is small and known.
- **Module toolbar standard:** search input, filter field(s), and the ONE primary action share a single toolbar row (`flex flex-wrap items-center gap-2` — wraps rather than spilling into a second disconnected control cluster); never float the primary action separately over a map/canvas even if the source Figma frame shows it that way (a live "law" can override stale per-module Figma precedent — the zones/POIs Figma reference had `+Create` floating over the map; T-035 says move it into the row regardless). A filter trigger must show its OWN state as visible text inside the field (`All Tags` / `3 Tags` — not an icon-only funnel with an external caption) — reuse the "value text lives in the field" idiom, not a bare icon button, even though the OLDER `AppShell`/`live-monitoring-view` filter chrome is icon-only (that's the stale pattern being superseded, not the one to copy).

## Cumulative stacked-bar helpers hide a zero-value z-order bug (T-058, ifm-workforce Pulse)
- **A `cum(parts)` helper that computes `{color, width: acc/total}` per part, then renders `[...bars].sort by width desc` layered by z-index, silently BREAKS when a trailing part's value is 0.** `StatusBreakdownCard`'s bars are correct in isolation, but the CONSUMER'S `cum()` (three-line local helper, copy-pasted per panel) accumulates width even for a 0-value part — since `acc` doesn't change, a 0-value part gets the exact SAME cumulative width as the part before it. Array `.sort()` is stable, so the tie keeps source order, and the LATER (zero-value) segment gets a HIGHER z-index — painting directly OVER the real segment of the same width and making a legitimate 100%-amber ("12 Partial / 0 Gap") bar render as solid red. This reproduces as "the bar tone looks wrong" when the real bug is a full-opacity decoy segment stacked on top, not a wrong color assignment. Fix: filter `parts.filter(p => p.v > 0)` BEFORE the cumulative-sum loop (zero-width segments render nothing anyway, so this is a pure bugfix, not a behavior change) — audit any `cum`/`cumulative`/"stacked segments from parts" helper the same way; it's a copy-pasted three-liner, not a shared primitive, so grep every call site.
- **A "fully covered" band computed as `present === total` (exact equality) is unreachable once the population is large enough that SOME exception (a no-show, a late) is near-certain every period** — 8,040 workers/12 sites meant every site had ≥1 no-show every day, so "Fully covered" read 0 forever even though coverage was genuinely ~95%+. Any per-entity "fully X" boolean derived from a large aggregate should be a THRESHOLD band (`pct >= 0.95`), never an exact-match, once N is large — the client's own spec ("full ≥95%, gap <85%, partial between") is the right shape to ask for up front.
- **New DS component: `SearchableSelect` (`basics/searchable-select.tsx`)** — a select-like trigger (mirrors `SelectTrigger` classes exactly) that opens a popover with the DS search-field idiom (`SearchMd` + `pl-8` + "Search anything here") over a RADIO-style option list (icon slot per option, optional pinned non-filterable "All …" row). Reach for this over `LabeledSelect`/`PeoplePicker` whenever the option list is long/named (sites, zones, any reference-data module) rather than person-shaped or icon-less — neither existing shell fit without forking. Give its search `<input>` a `data-slot="searchable-select-search"` (or similarly unique) attribute: a page with more than one "Search anything here" input (the DS-law placeholder is intentionally reused everywhere) makes a plain `querySelector('input[placeholder=...]')` in a QA script grab the WRONG one silently (first DOM match, not the portaled popover's).

## T-094 capstone F1/F2 — Radix Popover close-on-select is opt-in, and a custom `render` override silently strands a new ctx field
- **Radix `Popover` never auto-closes on an option click inside a hand-rolled `<button>` list** (unlike `DropdownMenuItem`, which closes by design) — `report-builder.tsx`'s `SelectField`/`FilterDropdown` (single-select) looked identical to the correctly-behaving `MultiSelectField`/shell `FacetDropdown` (multi-select, which SHOULD stay open) but was missing the controlled `open`/`onOpenChange` + an explicit `setOpen(false)` in the option's `onClick`. Fix pattern: add optional `open?`/`onOpenChange?` to the shared trigger wrapper (backward-compatible — Radix is uncontrolled when both are `undefined`), then only the SINGLE-select consumer owns `useState` + closes on pick. Never add this to a multi-select's option handler — grep every consumer of the wrapper before changing it, since one shared trigger component can legitimately have both single- and multi-select callers.
- **A per-instance "Group by" native `<select>` rendered inside a view (`PipelineListView`) can't be moved "into the one toolbar row" by styling alone** — the toolbar row is a SIBLING rendered earlier by the parent shell (`AppShell.tsx`'s `ModuleToolbar`), not a wrapper around the view, so the fix is a real state-lift: add shell-level per-tab state (`groupColByModule`, mirroring `sortByModule`/`facetFiltersByModule`), render the facet-dropdown-styled trigger IN `ModuleToolbar` (gated on `activeModule.type==='pipeline' && activeTab.kind==='list' && data.columns`), and thread the selection down through `ModuleRenderContext.groupByCol` (new optional field) into the view as a plain read-only prop — the view no longer owns the control or its state at all, only applies it to `DataTable`'s `groupBy`.
- **A product `ModuleConfig.render` override silently bypasses every ctx field a DS-level module-registry fix relies on.** After wiring `ctx.groupByCol` through `module-registry.tsx`'s built-in pipeline renderer, grouping still did nothing on 3 of 7 modules (Onboarding/Transfers/Exits) — they all route through a shared product helper (`lifecycle/shared.tsx`'s `pipelineRenderWithBanner`, a `ModuleConfig.render` override that renders `PipelineListView` directly to inject a banner above it) which had its own fixed call to `<PipelineListView .../>` missing the new prop. Diagnostic: temporarily `console.log` the ctx value at BOTH the shell (`renderCtx` construction) and the suspected consumer render path — if the shell's log fires but the registry/view's doesn't, a custom `render` override is intercepting before the built-in renderer ever runs (`activeModule.render ? activeModule.render(ctx) : def.render(ctx)`). Grep every `ModuleConfig.render:`/wrapper-factory (`pipelineRenderWithBanner`-shaped helpers) for direct `<PipelineListView>`/`<KanbanView>` calls whenever a DS ctx field gains new plumbing — a shared wrapper used by N modules needs exactly one fix, but it's a SEPARATE file from the DS's own generic registry and easy to miss if you only grep the DS tree.
- **Verifying "grouping still functions" needs the ACTUAL grouped-header DOM, not just the pill label.** The toolbar pill can correctly show "Group by: Trade" (state wiring proven) while the table underneath renders zero group-header rows (a different wiring gap) — a screenshot glance can miss this if the picked column happens to look plausible in row order. Dump `document.querySelectorAll('table tbody tr')[0].className` (a group header row has a distinct `bg-muted/30` class + `border-b border-border` with no per-column cells) or count total `<tr>`s (a truly grouped render still has the SAME data-row count PLUS one header `<tr>` per distinct group value) before trusting a pill-only screenshot as proof.

## Step-tab strip must sit ON the line, not float above it (T-084)
- **The `StepWizardSheet` / wizard step-tab composition had the underline detached from its divider**: the header `<div>` carried `border-b border-border` at its OUTER edge (below extra `pb-4` padding), while each tab's active indicator was an `absolute -bottom-px` span positioned relative to the BUTTON — two independent lines, with a visible gap between them. The DS already has the correct idiom one file over (`app-shell/entity-detail.tsx` profile tabs): put `border-b border-border` directly on the TAB-ROW container (no extra bottom padding after it), give every tab the SAME `pb-2.5` (no absolute span), and let ONLY the active tab add `border-b-2 border-primary` — because inactive tabs don't add that 2px to their box, `align-items:center` naturally centers the row on the tallest (active) tab, so the active border lands flush on the container's own line. Fix at the shared level (`StepWizardSheet`) fixes every consumer (RoleSheet, AppSheet, `ProjectWizard`/Capture Project) at once; a product file that "reimplements it locally to avoid nesting a second `<Sheet>`" (ifm-workforce's `CreateEmployeeWizard`) must get the identical class-recipe fix by hand, and its own header/step-heading comments naming the old label need the same rename swept through.
- **A crashed dev-server transform pipeline is NOT the same defect class as HMR staleness.** `fetch('/src/<file>')` returning a normal-looking (but OLD) transform means HMR/cache staleness — restart per the standing "don't restart" caution only if truly stuck. But a `500` with `"message":"The service was stopped"` / `"The service is no longer running"` (esbuild's child process died) on an UNRELATED file too (e.g. `main.tsx`) means the whole server is dead for every consumer, not just your edit — that overrides a "do not restart" instruction, because nothing can be verified by anyone until it restarts, and a restart loses zero on-disk work. Kill the dead PID first (`--strictPort` will refuse to rebind over a stuck listener) then relaunch.
- **`ElementHandle.click()` is coordinate/hit-test based and can silently miss** when a just-closed Radix Sheet's overlay is still fading (T-064's pointer-events residue, one layer up: this time the CLICK lands on empty overlay space, not "nothing happens"). Symptom: the click call resolves `true` (element was found) but the app state never changes — reopening "Create" on what you think is the new module instead reopens the OLD module's wizard, fresh/reset. Fix: dispatch via `page.evaluate((el) => el.click(), handle)` (a direct DOM method call, bypassing CDP's synthetic-mouse hit-test) for any nav/rail click that follows a sheet-close in the same script.
- Puppeteer nav on an icon-only collapsed rail: query `button[aria-label], a[aria-label]` and match the attribute by exact equality — the visible rail item and any duplicate-labelled control elsewhere in the app can collide on `textContent`, but `aria-label` is authored to be unique per rail entry (module ids like "Workforce"/"Projects" are 1:1 with a single rail button in this shell).

## A fixed-width text cell that wraps on SOME rows but not others is a glyph-width fluke, not a logic bug (T-085, live-monitoring Shift Time column)
- **Same-length strings can straddle a wrap boundary row-to-row.** `live-monitoring-view.tsx`'s metric cell (`"HH:MM / HH:MM"`, always ~13 chars) had a fixed `w-[76px]` box with NO `whitespace-nowrap` — every row's string is the same character COUNT, but proportional-font digit glyphs aren't the same PIXEL width (some digit/space combos render a hair narrower), so some rows fit on one line and others wrap ("04:30 /" / "08:00") purely from which digits happen to appear. This reads to a client as "broken/doubled," not as an obviously-too-narrow column, because most rows look fine. Fix is two-part and neither alone is sufficient: `whitespace-nowrap` on the VALUE span (forces one line, would otherwise just overflow/clip the box) + widen the box enough that nowrap content actually fits (76px → 92px here) — `tabular-nums` is worth adding too (fixed digit width removes the row-to-row variance going forward, though nowrap+width alone already fixes the visible bug). Check whether the cell's grandparent is `overflow-auto`/`overflow-hidden` before trusting nowrap alone — clipped text is not better than wrapped text, both fail "never hides the tail" (T-065 retro).
- **A `data.listWidth` (or any per-instance sizing prop) that's already config-driven means "widen the panel" is a ONE-LINE product-config change, not a DS edit** — `live-monitoring-view.tsx`'s hybrid list panel reads `data.listWidth ?? 340` and the product already overrode it (380, from an earlier ticket); bumping the client's "expand a bit more" ask was `380 → 420` in the product's module config, zero DS changes needed. Always check whether the "hardcoded px" the ticket describes is actually a config default with a per-product override already in place before touching DS source.

## Status-idiom vs action-idiom typography (T-086, StateTransitionToolbar + ActivityFeed)

## Windowed lazy-scroll DataTable (T-087, replacing every Prev/Next page footer) — design + a real virtualization bug
- **The windowing design that survives scroll-away-and-back:** a monotonic "revealed so far" frontier (`loadedCount`, grows in `chunkSize` batches via a bottom-sentinel `IntersectionObserver`) is NOT the mount window by itself — the mount window (`range`) must be recomputed from the CURRENT `scrollTop` every time (clamped to `[0, loadedCount)`, hard-capped to `windowSize`), so scrolling back UP re-mounts an already-revealed row instead of leaving it behind a monotonic tail-eviction. This only works because a windowed row is STATELESS (its value comes from the `data` prop, not local state) — any consumer with an editable cell (payroll Worksheet) MUST lift the edit into the consumer's own state (keyed by row id), never a per-row `useState`, or the value is lost on unmount/remount.
- **A big instantaneous `scrollTop` jump (scrollbar drag, or a puppeteer script setting `el.scrollTop = X` directly) can outrun `loadedCount` before the sentinel ever gets a chance to intersect it** — `end` clamped to the stale (smaller) `loadedCount` while `start` (pure scrollTop math) keeps climbing produces an INVERTED `start > end` slice: zero rows render, the top spacer keeps growing to match scrollTop, and the container's `scrollHeight` grows WITHOUT BOUND (a real, reproducible bug I hit and fixed — verify any hand-rolled virtualization the same way: jump `scrollTop` to a huge value in one step, not just incrementally, and check `dataRows > 0`). Fix: in the SAME recompute pass, if the desired window's end exceeds `loadedCount`, bump `loadedCount` synchronously (functional `setState`, rounded up to whole `chunkSize` units) and use that NEW value for `end` immediately — don't wait for a second render or the sentinel.
- **Sticky `<thead>` MUST be a fully OPAQUE background, not a tinted/alpha variant** (`bg-muted/40` let scrolled rows bleed through — client-reported as a row's text showing through the header). Once a table is its own scroll region (the whole point of `scrollMode="lazy"`), this is no longer a cosmetic nit — sweep for it via `grep "sticky.*bg-\w*/[0-9]"` across every table-ish component in scope; if every table in the product routes through one shared `DataTable`, the fix is one line at the source, not a per-consumer sweep.
- **Toolbar single-select fields (Group-by, a Trade/type scoper) must share EXACT box anatomy with the shell's own facet-dropdown trigger** (`h-10 rounded-lg border px-3 text-body-sm font-medium` + muted leading icon + trailing `ChevronDown`, `border-primary bg-secondary` tint once non-default) — a generic `<Select>`/`SearchableSelect` default trigger reads as a foreign pill next to them. Fix pattern: rebuild the trigger as a `Popover`+button pair with those exact classes (or pass them via `triggerClassName` if the component supports it, e.g. `SearchableSelect`), and bridge state between the field (rendered via `ModuleConfig.toolbarSlot`) and the module's own `render()` content — two separate React subtrees — via a tiny module-scope external store (`useSyncExternalStore`), the same recipe `workforce.tsx`'s Group-by field established; reuse it verbatim for the next one rather than re-deriving it.
- **A consumer's `data` array passed to `scrollMode="lazy"` MUST be memoized (`useMemo`) with real dependency tracking** — the lazy window resets whenever the `data` prop's REFERENCE changes, so an unmemoized inline filter (recomputed every render, including renders triggered by the lazy table's own `onLazyProgress` callback) resets the scroll window on every single frame, which silently reads as "scrolling doesn't work" (found and fixed one real instance: `skills-matrix.tsx` computed `filtered` inline).
- **`page.metrics().Nodes` (CDP `Performance.getMetrics`) was WILDLY unreliable in this shared, HMR-active dev server** — swinging 5x-10x between otherwise-identical measurements taken seconds apart, while `document.querySelectorAll('*').length` (a direct DOM query) stayed sane and exactly proportional to the actual rendered row delta. Trust the direct DOM count as the authoritative "nodes stayed bounded, not cumulative" perf proof in an environment with concurrent fixers triggering Vite HMR; cite the CDP metric only as a secondary datapoint with this caveat.
- **A QA/puppeteer script's `document.querySelector('table')` silently grabs the WRONG table once a Sheet/Dialog stacks a second one over a background list-view table** — Radix `role="dialog"` content still shares the document, and DOM order (not visual z-order) decides which `querySelector` returns; scope to `[role="dialog"] table` (falling back to the plain page table when nothing's open) before scrolling/editing/reading a row inside an opened detail sheet, or you'll silently test the wrong surface with no error (this cost a full debugging cycle before catching it: the "worksheet edit-survives-scroll" proof kept reading `null`/`found:false` until scoped correctly).
- **A synthetic `el.scrollTop = X; el.dispatchEvent(new Event('scroll'))` jump needs a real settle delay (~2s) before a screenshot/metrics read**, especially after a very large jump — a screenshot taken immediately can catch an in-between repaint frame that looks like a real bleed-through/layout bug but resolves cleanly on the next frame. Don't diagnose a rendering defect from an unsettled screenshot; re-shoot with a longer sleep first to rule out a timing artifact before concluding it's a real bug.

## Category-scoped "assign by X" picker (T-097, EventConfigSheet Assign Entity) — a reusable radio→checkbox pattern
- **A left radio-group "scope category" next to a right checkbox grid must key the grid's VISIBLE OPTIONS off the selected category, not render one shared flat list beside the radios** — `EventConfigSheet`'s `assetTypes: string[]` (one global vocabulary) looked fine with the DS's own generic fleet default (Assets/Devices/Workforce, only one category populated) but broke the instant a real consumer (ifm-workforce: Sites/Trades/Camps/Bus-Routes, all four populated) passed a genuinely multi-category catalogue — every category's members rendered together in one mixed grid regardless of which radio was selected. ## DS-wide font-size normalization sweep (Tailwind defaults/arbitrary px → semantic type scale)
- **A blind `\btext-(xs|sm|base|lg|xl|2xl|3xl)\b` / `\btext-\[Npx\]\b` regex swap across `src/components/**/*.tsx` is safe with ZERO substring collisions** — `text-sm` never matches inside `text-body-sm` (the literal substring `text-sm` doesn't occur there; `text-` is always immediately followed by `body-`), and default-scale names (`xl`/`2xl`/`3xl`) don't collide with each other either, since the char right after `text-` always disambiguates which alternative can match. Recharts/SVG `fontSize={11}` numeric props and `text-[color:var(...)]`/`text-[#hex]` arbitrary COLOR values are untouched by construction (the size regex requires literal digits + `px` inside the brackets).
- **Not every arbitrary px value has a safe nearest-token mapping — some are genuinely ambiguous (equidistant between two tokens) and some have no good candidate at all.** `text-[22px]` (equidistant 20/24) and `text-[26px]` (equidistant 24/28) were left unmapped in `entity-detail.tsx`/`task-detail.tsx` (heading-sized page titles) rather than guessed. `text-[8px]` (`map-marker.tsx`'s tiny `size-4` circular badge digit) has no lower token at all (nearest is `text-caption`=12px, a 50% size jump that would visually overflow a 16px badge) — the overarching "never change rendered size" constraint outranks a mechanical "always map to nearest token" instruction when the nearest token is a poor real-world fit; leave it and report rather than force a token that breaks the container.
- **13px has exactly one sanctioned exception baked into the task spec (round UP to `body-sm`=14, not down to `caption`=12)** — worth double-checking any similar sweep's spec for a stated rounding direction before assuming "nearest" always means strict numeric distance.
